# 🗃️ 02 · 向量数据库与 RAG 工程

> RAG 落地的「工程心脏」是向量库。选型、索引、性能、成本直接决定效果与体验。详见 `03-AI Agent/02-RAG` 原理，本篇讲工程实现。

---

## 一、主流向量库对比

| 向量库 | 特点 | 适用 |
|--------|------|------|
| **Milvus** | 分布式、企业级、功能全 | 大规模生产 |
| **pgvector** | PG 插件，复用关系库 | 中小规模、少运维 |
| **FAISS** | 高性能单机库（Meta） | 嵌入应用/原型 |
| **Qdrant / Weaviate** | 云原生、易用 | 中等规模 |
| **Redis / Elasticsearch** | 已有则复用 | 轻量/全文本+向量 |

## 二、索引与检索
- **ANN 索引**：HNSW（图，快、内存大）、IVF（倒排，省内存）、PQ（量化压缩）
- **距离度量**：余弦（最常用）、内积、欧氏
- **维度**：embedding 通常 768/1024/1536 维
- **混合检索**：向量（语义）+ BM25（关键词）→ RRF 融合，效果最佳

## 三、工程要点
- **分块策略**：按语义/标题切，overlap 防断义；块大小影响召回与噪声
- **元数据过滤**：先按时间/来源/权限过滤再检索（降本提准）
- **写入/更新**：文档变更要增量更新向量，避免全量重建
- **一致性**：多租户隔离（见 `07-后端`）
- **性能**：批量嵌入、异步入库、缓存热点查询

## 四、RAG 质量调优清单
- [ ] 召回率够吗？（换 embedding / 加 BM25 / 调 top-k）
- [ ] 排序准吗？（加重排 rerank）
- [ ] 上下文噪声？（压缩/筛选相关句）
- [ ] 忠实度？（要求仅基于片段、给引用）
- [ ] 端到端评测？（RAGAS：faithfulness/context recall/answer relevancy）

## 五、高频追问
**Q1：HNSW 和 IVF 怎么选？**
> HNSW 查询快但内存占用大，适合追求低延迟；IVF 省内存、可扩展到超大库，适合成本敏感/超大规模。常配合 PQ 压缩。

**Q2：为什么需要混合检索？**
> 向量擅长语义、弱于精确关键词（如专有名词/编号）；BM25 擅长精确匹配。融合互补，显著提升召回质量。

**Q3：向量库数据怎么和源文档保持一致？**
> 文档变更触发增量重新嵌入与 upsert，旧向量删除；用版本/etag 追踪；定期全量校验，避免脏数据。
