# 🔗 04 · MCP 与多 Agent（Multi-Agent）

> 当单个 Agent 不够用时：用 MCP 标准化工具接入，用多 Agent 协作分工。本篇讲「规模化」。

---

## 一、MCP（Model Context Protocol）

**问题**：每个 Agent 框架都要自己写工具适配，工具无法复用、生态割裂。

**MCP 的思想**：定义一套**标准化协议**，让「模型」与「工具/数据源」解耦——就像 USB-C 统一接口。

- **MCP Server**：暴露工具/资源（如查数据库、读文件、调 API）
- **MCP Client**：Agent 通过标准协议调用 Server
- **好处**：工具一次开发，任意兼容 MCP 的 Agent 都能用；安全边界清晰

> 本质判断：MCP 是「工具接入标准」，不是 Agent 框架本身。它解决的是**互操作性与复用**，跨周期价值在于「降低集成成本」。

---

## 二、多 Agent 协作（Multi-Agent）

**动机**：单 Agent 上下文有限、易顾此失彼；分工可提升复杂任务质量。

### 常见协作模式
1. **主管-下属（Supervisor-Worker）**：一个 Orchestrator 拆解任务，派给专门 Agent（检索/编码/写作）。
2. **流水线（Pipeline）**：Agent A 产出 → Agent B 消费，串行。
3. **辩论/评审（Debate）**：多个 Agent 各执观点，互评收敛（提升推理质量）。
4. **角色扮演**：不同专家角色协作（如产品经理+工程师+测试）。

### 通信机制
- 共享黑板（Blackboard）/ 消息总线
- 结构化消息（JSON）、共享记忆
- 主管调度或事件驱动

### 冲突与协调
- **任务冲突**：主管仲裁、优先级队列
- **结果不一致**：投票/评审/一致性校验
- **上下文膨胀**：每个子 Agent 只看自己相关上下文，主管汇总

---

## 三、何时用多 Agent？（避免过度设计）

| 用单 Agent | 用多 Agent |
|------------|------------|
| 任务单一、工具少 | 任务复杂需分工 |
| 成本/延迟敏感 | 质量优先、可并行 |
| 快速原型 | 生产级、需专业化 |

**成本提醒**：多 Agent = 多轮 LLM 调用，token 成本和延迟显著上升。先问「单 Agent + 好工具」能否解决。

---

## 四、高频追问

**Q1：MCP 解决了什么痛点？**
> 工具/数据源与 Agent 强耦合、无法复用。MCP 用标准协议解耦，一次开发多端复用，降低集成成本、明确安全边界。

**Q2：多 Agent 一定比单 Agent 好吗？**
> 不一定。多 Agent 增加成本和复杂度，只在「确实需要分工/并行/专业化」时收益明显；很多场景单 Agent + 好工具 + 反思即够用。

**Q3：多 Agent 怎么解决冲突？**
> 主管仲裁、结果评审/投票、共享一致记忆、明确各 Agent 职责边界，必要时加校验 Agent。
