# 🔄 01 · Agent 架构范式（ReAct / Plan-and-Execute / Reflexion）

> Agent 的「大脑运转方式」。面试最爱问「为什么选 ReAct 而不是 Plan-and-Execute」——本题考的是**架构权衡判断力**。

---

## 一、ReAct（Reasoning + Acting）⭐ 最经典

**思想**：把「思考（Thought）→ 行动（Action）→ 观察（Observation）」串成循环。

```
Thought: 我需要查天气，先调用天气工具
Action: get_weather(city="北京")
Observation: 北京 25°C 晴
Thought: 已知答案，回复用户
Action: Final Answer: 北京今天25°C晴
```

- 每步基于**当前观察**动态决策，**强交互、强适应**。
- 天然兼容 Function Calling。

**优点**：灵活、可处理突发情况、易用 few-shot 调。
**缺点**：长任务易「走偏/循环」、缺乏全局规划、token 消耗大。

---

## 二、Plan-and-Execute（先规划再执行）

**思想**：先用一个「规划器」把任务拆成步骤计划，再逐步执行；执行中可重规划。

- 适合**复杂、长链条、可预见的任务**（如「调研+写报告」）。
- 代表：Plan-and-Solve、LangGraph 的 plan 模式。

**优点**：有全局观、不易跑偏、可并行子任务。
**缺点**：初始计划可能不准、对动态环境适应性弱、规划器本身可能出错。

---

## 三、Reflexion（反思/自我修正）

**思想**：Agent 执行后**自我反思**失败原因，把反思写进记忆，下一轮改进。

- 常用于代码生成、需要迭代优化的任务。
- 关键：把「错误+反思」作为额外上下文反馈给模型。

---

## 四、范式对比与选型（⭐ 面试核心）

| 范式 | 适配场景 | 不擅长 |
|------|----------|--------|
| ReAct | 实时交互、工具调用、动态任务 | 很长/需严格顺序的任务 |
| Plan-and-Execute | 复杂多步、可规划任务 | 高度不确定/需即时反应 |
| Reflexion | 可验证、需迭代（代码/搜索） | 一步即得的简单任务 |
| ReAct + 反思 | 大多数生产场景（主流组合） | 极低成本要求 |

**选型判断框架**：
1. 任务是否可预先规划？→ 是：Plan-and-Execute；否：ReAct。
2. 是否需要从错误中学习？→ 是：加 Reflexion。
3. 成本/延迟敏感？→ 减少反思轮次、用轻量规划。

---

## 五、高频追问

**Q1：为什么选 ReAct 而不是 Plan-and-Execute？（经典题）**
> 看场景。实时客服/工具调用这类需动态适应、无法预先规划的任务 → ReAct；长链条研究写作类可先规划 → Plan-and-Execute。生产常「Plan 打底 + ReAct 执行 + Reflexion 纠错」混合。还可在 ReAct 中加 few-shot 让它近似规划，灵活性与可预测性权衡。

**Q2：ReAct 最常见的失败场景？怎么缓解？**
> 循环（重复同动作）、幻觉工具参数、长上下文遗忘。缓解：最大步数限制、循环检测、把关键结果写入记忆、加校验节点。

**Q3：为什么现在很多项目不用重框架而自研核心循环？**
> 重框架抽象多、启动慢、定制难；多数场景核心只是「循环 + 工具 + 记忆」，自研更可控、易调试、成本低。框架适合快速原型。
